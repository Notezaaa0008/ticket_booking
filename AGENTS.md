# PROJECT: Ticket Booking System

## 0. Mission
Build a web application where users search showtimes and seats, book tickets,
pay, and receive tickets. Admins manage events, showtimes, and bookings.
This is an interview assignment: correctness, clarity, and reviewability matter
more than feature count. A smaller system that works and is tested beats a larger
one that is half-working.

## 1. Tech stack (do not change without asking)
- Frontend: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui, in /frontend
- Backend: Go 1.22+, Gin, GORM (postgres driver), in /backend
- Database: PostgreSQL 16 (source of truth)
- Cache/lock: Redis 7 via go-redis v9 (seat hold, cache, rate limit only)
- Auth: JWT (access token) + bcrypt password hashing
- Migrations: plain SQL files with golang-migrate in /backend/migrations
  (do NOT use GORM AutoMigrate for schema changes)
- Local infra: docker-compose.yml at repo root (postgres + redis)
- Tests: Go `testing` + testify; frontend uses lint + type-check (+ Playwright for key flows)

## 5. Backend conventions
- Layering: handler -> service -> repository. Handlers contain no business logic.
- All routes under /api/v1. Responses are JSON. Error shape:
  {"error": {"code": "SEAT_UNAVAILABLE", "message": "human readable"}}
- Use context.Context on every DB/Redis call. Set timeouts.
- IDs are UUIDs (generated by Postgres gen_random_uuid()).
- Money is an integer in satang (int64). NEVER use float for money. Currency is THB.
- Timestamps are UTC (timestamptz). The frontend formats to local time (Asia/Bangkok).
- Validate all input with binding tags or explicit checks. Never trust client-supplied
  prices, totals, user ids, or roles. Price always comes from the DB.
- Config only from environment variables (see .env.example). Never hardcode secrets.
- Log with structured logs. Never log passwords, tokens, or full card data.
- Return proper HTTP status: 400 validation, 401 unauthenticated, 403 forbidden,
  404 not found, 409 conflict (seat taken, duplicate), 422 business rule, 500 unexpected.

## 6. Booking safety rules (NON-NEGOTIABLE)
- PostgreSQL is the source of truth. Redis only speeds things up.
- A seat can have at most ONE active booking item. Enforced by a partial unique index
  on booking_items(seat_id) WHERE active = true. Do not remove or weaken it.
- Seat hold flow: (1) Redis SET hold:{seat_id} {booking_id} NX EX {ttl} for each seat;
  if any fails, release those already acquired (only if the value matches) and return 409;
  (2) in ONE DB transaction create booking (PENDING, expires_at) + booking_items (active=true);
  a unique violation means conflict -> rollback, release Redis keys, return 409.
- If Redis is unavailable, fall back to DB-only behavior (the unique index still protects us)
  and log a warning. Never oversell because Redis is down.
- Expired PENDING bookings must be released: a background job every 30s sets booking
  EXPIRED and booking_items.active=false; booking creation also lazily expires stale holds
  on the requested seats.
- Payment confirmation must run in one transaction with SELECT ... FOR UPDATE on the booking.
  It must be idempotent: the same webhook event twice must not create two tickets.
- Webhook requests must verify an HMAC-SHA256 signature using PAYMENT_WEBHOOK_SECRET
  (constant-time compare). Reject invalid signatures with 401.
- Every concurrency-sensitive change requires a test that proves it (parallel goroutines
  booking the same seat: exactly one succeeds).

## 7. Frontend conventions
- TypeScript strict. No `any` unless commented why.
- All API calls go through /frontend/src/lib/api.ts. Base URL from NEXT_PUBLIC_API_URL.
- Every page handles loading, empty, and error states.
- Seat map must show 3 states clearly: available / held / sold, plus "selected".
- Never compute prices on the client for authority; display what the server returns.
- Store the JWT in memory + httpOnly-safe approach if possible; if localStorage is used,
  note the trade-off in docs. Ask the human before choosing (Section 10).
- Keep UI simple and accessible (labels, button states, keyboard focus). Do not spend
  time on heavy styling.

## 8. Testing rules
- Every new service function gets unit or integration tests.
- Integration tests use the real docker-compose Postgres/Redis with a separate database
  named ticket_booking_test. Never run tests against the dev database.
- Required tests by the end of the project: double-booking race, hold expiry,
  duplicate webhook idempotency, invalid webhook signature, admin-only access (403 for users),
  payment after expiry.
- Do not delete or weaken a failing test to make it pass. Fix the cause or ask the human.

## 9. Definition of Done (evidence required)
Never say "done", "complete", or "working" unless the final message contains:
1. The exact commands you ran and their REAL output (copy/paste, not summarized):
   backend vet + test, frontend lint + tsc + build (when frontend changed).
2. A checklist table mapping each acceptance criterion of the phase to the file/line
   or test name that proves it, with status PASS / FAIL / NOT DONE.
3. A list of anything you did not do, skipped, mocked, or are unsure about.
4. Any deviation from the plan and why.
If a command fails, report the failure honestly. Do not hide, truncate, or reinterpret errors.
Saying "should work" is not evidence.

## 10. STOP and ask the human before doing any of these
- Creating or changing database schema / migrations
- Changing booking, seat hold, locking, or transaction logic
- Anything in payment flow: statuses, webhook handling, idempotency, refunds
- Authentication, password handling, JWT settings, roles/permissions
- Adding or upgrading dependencies
- Creating/changing .env files or anything that holds secrets
- Business rules: cancellation, refund, hold duration, max seats per booking, pricing
- Deleting files or rewriting large parts of existing code
- Changing this file, docs/plan.md, or docs/schema.md
